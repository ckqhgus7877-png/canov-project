# Claude 구현 프롬프트 08 - CANOV 랜딩 페이지 비공개 미리보기

## 1. 역할과 목표

당신은 CANOV 프로젝트의 구현 담당자다. 아래 기획 문서를 근거로 브랜드 랜딩 페이지, 테스트 신청 API와 Cloudflare Access로 보호되는 읽기 전용 신청 확인 화면을 구현한다.

첫 목표는 공개 서비스가 아니라 `로컬 검사 → 보호된 미리보기 → 사용자 검토`가 가능한 검증용 결과다. 실제 고객 개인정보와 운영 데이터는 사용하지 않는다.

## 2. 반드시 읽을 기준 문서

- `README.md`
- `docs/handoff/CURRENT.md`
- `docs/planning/CANOV-QNA-checkpoint-v0.1.md`
- `docs/planning/CANOV-landing-page-acceptance-v0.1.md`
- `docs/planning/CANOV-landing-page-architecture-v0.1.md`
- `docs/planning/CANOV-PRD-v0.4-cs-automation.md`
- `docs/planning/CANOV-development-tools-plan.md`
- `docs/references/CANOV-Brand-Story.pdf`

문서가 충돌하면 최신 Q&A 체크포인트, 랜딩 페이지 완료 조건, 기술·보안 결정 순으로 우선한다. 미정 또는 자료 수령 대기 항목을 임의로 확정하지 않는다.

## 3. 확정 기술 조합

- Astro + TypeScript
- Cloudflare Workers용 공식 Astro 어댑터
- 별도 Supabase 테스트 프로젝트
- Cloudflare Access로 미리보기 호스트 전체 보호
- 패키지 관리자는 저장소에서 기존 기준이 없으면 `pnpm` 사용

호환되는 안정 버전을 사용하고 lockfile을 커밋한다. 실제 배포 계정 생성, 유료 전환, 도메인 구매와 공개 배포는 사용자 승인 없이 수행하지 않는다.

## 4. 결과물 위치

- 랜딩 페이지 앱: `apps/website/`
- 재현 가능한 데이터베이스 마이그레이션: `backend/supabase/migrations/`
- 테스트용 seed 또는 예시 데이터: `backend/supabase/seed/`
- 환경 변수 예시: 실제 값이 없는 `.env.example`
- 구현·검증 결과 보고: `reviews/08-landing-page-initial.md`

기존 파일과 사용자 변경을 보존한다. 범위를 벗어난 앱·관리자 웹·결제 기능은 만들지 않는다.

## 5. 고객 랜딩 페이지 범위

다음 서사를 자연스럽게 연결한다.

1. 브랜드 인트로와 `Your Car, Always Cared For.`
2. 차량 관리를 계속 미루게 되는 고객 문제
3. `차량 관리가 고객의 일이 아니게 만들 수 없을까?`라는 출발 질문
4. 첫 신청 이후 매번 예약하지 않아도 이어지는 정기 방문
5. CANOV Care Profile
6. 방문할수록 누적되는 관리 이력
7. 담당자가 달라도 유지되는 표준 작업 기준과 품질 확인
8. 서비스·가격 안내
9. 운영 가능 단지 검색과 서비스 지역 요청
10. 테스트 신청서와 카카오톡 상담 연결

브랜드 PDF의 사진은 실제 CANOV 작업 사례 또는 동일 차량 전후 사진으로 표시하지 않는다. 사용 권한이 불분명한 이미지를 새 사이트 자산으로 무단 추출하지 않는다. 우선 대체 가능한 이미지 영역과 적절한 대체 텍스트를 구성한다.

간단한 차량 관리 방향에는 타이어 공기압·워셔액 같은 점검과 보충이 포함된다. 안전하게 수행 가능한 상태 점검은 기본 제공하고, 실제 보충은 Care Profile의 차량별·항목별 상시 동의와 차량별 기준 확인 후 진행하는 것으로 구분한다. 고객은 항목별 동의를 철회할 수 있다. 이를 수리·분해·고장 진단·법정 점검을 제공하는 정비 서비스로 확대해 표현하지 않는다. 세부 항목, 동의 변경 경로, 가격, 차종 등급, 부가세와 예외 차종은 확정 자료보다 넓게 표현하지 않고 미정 정보는 데이터 설정과 화면 문구에서 구분한다.

## 6. 테스트 신청서

비공개 미리보기임을 명확히 알리고 실제 이름·전화번호 대신 테스트 값을 입력하도록 안내한다. 운영 주체 정보가 확정 전임을 표시하며 실제 운영자로 오인할 임의의 이름, 사업자명, 전화번호나 이메일을 만들지 않는다. 개인정보 문의는 향후 CANOV 보유 도메인의 역할 주소와 일반 상담에서 분리된 유료 업무용 메일함을 공식 창구로, 카카오톡·CS를 보조 경로로 제공할 예정이라고만 표시하고 실제 주소나 링크를 추측하지 않는다. 도메인·메일·인증번호 발송 제공업체나 요금제를 구현 중 임의로 선택·가입·구매하지 않으며 개인정보 메일함, 휴대전화 인증과 CS 자동화 연동도 이 범위에서 구현하지 않는다. 후속 자동화는 분류·승인된 접수 안내·사람 검토용 초안까지만 허용하고 실제 개인정보 조치를 자동 실행하지 않는다는 미정 범위 안내를 구현 보고서에 남긴다. 미리보기용 표시값과 향후 운영 설정을 분리하고, 이 단계에서는 실제 개인정보를 받는 공개 신청 기능이나 공개 배포를 구현하지 않는다.

최소 검증 필드:

- 테스트 신청자 이름
- 테스트용 휴대전화 형식
- 아파트 선택 또는 서비스 지역 요청 입력
- 차량 모델과 차량 구분 후보
- 연락 희망 방식

차량번호, 상세 주차 위치, Care Profile과 보충 항목별 동의는 첫 신청서에서 받지 않는다. 첫 공개 버전에는 마케팅 수신 동의 항목을 표시하거나 그 동의값을 수집하지 않는다. 개인정보 처리의 목적·항목·보유기간과 온라인 신청 선택 권리를 신청 버튼 전에 바로 표시하고, 전문은 입력값을 잃지 않는 접근 가능한 펼쳐보기로 제공한다. 개인정보 처리방침 링크도 함께 제공한다. 개인정보 수집·이용 필수 동의 체크박스와 동의값은 만들지 않는다. 상담 종료·철회 시 지체 없이 파기하고 미응답·미계약 신청은 고객의 마지막 의미 있는 응답 또는 무응답 시 접수일로부터 최대 90일 후 파기하는 구조를 반영한다. 서버가 관리하는 적용 안내 문구 버전과 적용 시각을 기록하며 브라우저가 보낸 임의의 버전을 신뢰하지 않는다. 동의한 것으로 기록하거나 불필요한 IP·기기정보를 추가 수집하지 않는다. 실제 공개 신청서의 최종 문구와 운영 주체 정보는 임의로 만들지 않는다. 고지안의 법적 근거는 공개 전 실제 운영 흐름에 맞춰 최종 검토 대상임을 구현 보고서에 남긴다. 향후 실제 캠페인 계획과 사용자 승인이 생기면 마케팅 동의를 별도 선택 항목으로 추가할 수 있게 범위를 분리한다.

클라이언트와 서버에서 모두 필수값, 길이, 형식과 허용값을 검증한다. 오류는 입력 항목 가까이에 텍스트로 표시하며 다른 정상 입력값을 유지한다.

## 7. Workers 신청 API

- 브라우저에서 Supabase 테이블을 직접 호출하지 않는다.
- 허용된 필드만 명시적으로 추출한다.
- 서버에서 입력을 다시 검증한다.
- 서버 또는 데이터베이스가 접수 UUID와 접수 시각을 생성한다.
- 클라이언트가 생성한 idempotency key와 데이터베이스 고유 제약으로 중복 제출을 방지한다.
- 저장 성공 후에만 성공 응답과 접수번호를 반환한다.
- 오류 응답은 내부 정보, 키, SQL과 스택 추적을 노출하지 않는다.
- 속도 제한 또는 봇 방지를 연결할 수 있는 경계를 마련한다.
- 후속 카카오톡·SMS 발송은 구현하지 않되 저장 이후 별도 처리로 추가할 수 있게 결합도를 낮춘다.

## 8. Supabase 구조와 보안

테스트에 필요한 최소 테이블만 만든다.

- `service_areas`: 운영 단지 검색용 테스트 기준정보
- `registrations`: 테스트 신청, 접수번호, 서버 시각, idempotency key, 테스트 표시와 입력 데이터

요구사항:

- 외부 노출 테이블에 RLS 활성화
- 역할별 GRANT와 RLS를 함께 정의
- 브라우저의 `registrations` SELECT·INSERT·UPDATE·DELETE 기본 차단
- 서버용 secret key 또는 legacy service role key는 Workers 환경 변수에서만 사용
- 키, 실제 `.env`, 토큰과 테스트 신청 원문을 Git 또는 로그에 저장하지 않음
- 스키마의 NOT NULL, CHECK, 길이와 UNIQUE 제약으로 잘못된 값을 차단
- 상담 상태, 마지막 고객 응답 시각과 `retention_expires_at`을 분리해 운영자의 일방적 연락만으로 만료일이 연장되지 않게 함
- 허용·차단 정책 테스트 작성

가능하면 현재 권장 publishable key·secret key 명칭을 사용한다. 비밀 키가 브라우저 번들에 포함되지 않았는지 빌드 결과에서도 확인한다.

## 9. 신청 완료 화면

정상 저장 후 다음을 표시한다.

- 테스트 신청 접수 완료
- 접수번호
- 접수 시각
- 예상 연락 절차가 후속 운영 정책에서 확정된다는 안내
- 카카오톡 상담 버튼 또는 채널 주소 미확정 상태의 안전한 대체 문구

첫 버전에서는 실제 카카오톡·SMS 자동 메시지를 발송하지 않는다.

## 10. 읽기 전용 신청 확인 화면

Cloudflare Access로 보호되는 미리보기 호스트 안에 비개발자용 최소 확인 화면을 만든다.

필수 기능:

- 테스트 신청 목록
- 테스트 데이터 배지
- 접수번호, 접수 시각, 아파트, 차량 구분, 연락 희망 방식
- 접수번호·아파트 검색
- 기본 필터
- 읽기 전용 신청 상세
- 목록 연락처 일부 마스킹
- 빈 상태, 로딩, 조회 실패와 재시도 안내
- 모바일과 데스크톱 대응

제외 기능:

- 수정
- 삭제
- 일괄 처리
- CSV 등 파일 내보내기
- Supabase 설정 노출

화면에서 버튼을 숨기는 것만으로 보호하지 않는다. 조회 API와 미리보기 호스트 전체가 Cloudflare Access 정책 아래에 있어야 한다. 공개 운영 도메인에는 이 관리자 경로를 배포하지 않거나 접근 불가능하게 분리한다.

## 11. Cloudflare Access와 환경 분리

- `preview` 또는 `staging` 전용 호스트만 Access로 보호한다.
- 승인된 이메일·계정 또는 이메일 일회용 인증을 사용한다.
- 검색엔진 차단도 함께 적용한다.
- 운영 도메인에 Access를 적용하지 않는다.
- Access 우회 토큰이 필요한 자동 테스트는 환경 변수에서만 읽는다.
- 로컬·미리보기·운영 환경 변수와 Supabase 프로젝트를 분리할 수 있게 구성한다.
- 실제 Cloudflare·Supabase 설정 단계는 README에 재현 가능하게 기록하되 비밀값은 넣지 않는다.

## 12. UX·접근성·반응형

- 모바일 우선으로 구현하되 태블릿과 데스크톱에서도 레이아웃이 안정적이어야 한다.
- 키보드만으로 전체 주요 흐름을 수행할 수 있어야 한다.
- 모든 입력에 연결된 label, 오류 설명과 명확한 포커스 스타일을 제공한다.
- 색상만으로 상태를 구분하지 않는다.
- 핵심 이미지에 의미 있는 대체 텍스트를 제공한다.
- 제출 중 상태와 중복 클릭 방지를 시각적으로 알린다.
