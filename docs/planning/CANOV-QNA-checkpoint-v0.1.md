# CANOV 기획 Q&A 체크포인트 v0.1

작성일: 2026-09-15
상태: 진행 중. 전체 Q&A 종료 후 통합 PRD로 정리하기 위한 중간 기록이다.
참여: 사용자, 우현, Codex(PM)

## 기록 원칙

- 아래 항목은 대화에서 선택된 현재 방향이다.
- 우현의 세차 상품·제공 범위 자료가 필요한 부분은 확정하지 않는다.
- 결제대행사, 환불 기준, 상세 상품 체크리스트와 사진 기준은 후속 결정 대상이다.
- 마지막 미답변 질문부터 Q&A를 재개한다.

## 1. 정기 방문 주기와 가격

- 상품 기준: 외부 정기관리.
- 결제 단위: 월 이용료.
- 방문 주기: 매주 1회.
- 해당 결제 주기에 지정 방문 요일이 5번 있으면 추가 요금 없이 5회 방문한다.
- 아파트 방문 그룹별 고정 요일·시간대를 운영자가 정한다.
- 고객에게는 정확한 시각 대신 방문 시간대를 안내한다.
- 고객은 매주 별도 예약하지 않는다.
- 3개월 등록 시 1개월 무료 프로모션은 적용하지 않는다.

| 차량 구분 | 월 이용료 | 비고 |
|---|---:|---|
| 소형 | 40,000원 | 매주 1회 |
| 중형 | 50,000원 | 매주 1회 |
| 대형 | 60,000원 | 매주 1회 |
| SUV | 50,000원부터 | 정확한 분류 기준 자료 대기 |
| 대형 SUV·승합·특수 차종 | 별도 문의 | 자료 대기 |

차종 분류, 세부 제공 범위, 부가세 표시, 상세 작업 항목은 우현 자료를 받은 후 디벨롭한다.

## 2. 예약·배정·작업 상태

### 자동 예약

- 정기관리 활성화 후 시스템이 방문 그룹 일정에 맞춰 예약을 자동 생성한다.
- 항상 앞으로 4주간 예약이 존재하도록 순차 생성한다.
- 같은 차량·같은 방문일의 중복 예약을 만들지 않는다.
- 미래 예약은 삭제하지 않고 상태와 이력으로 보존한다.

### 정상 흐름

`자동 예약 생성 → 배정 대기 → 방문 예정 → 작업 중 → 품질 확인 → 완료`

- 관리자가 디테일러를 배정하면 별도 수락 없이 즉시 확정된다.
- 차량 확인, Care Profile 확인, 필수 기록 조건을 만족해야 작업을 진행할 수 있다.
- 현장 도착·이동 중 상태는 첫 버전에 두지 않는다.

### 보완 작업

`품질 확인 → 보완 작업 → 품질 확인 → 완료`

- 보완 사유와 보완 항목·사진을 기록한다.

### 작업 불가

`방문 예정 → 디테일러 작업 불가 처리 → 작업 불가 → 보충 예약 자동 생성`

- 디테일러가 관리자의 사전 승인 없이 직접 확정할 수 있다.
- 작업 불가 사유와 상세 메모는 필수다.
- 차량 미확인·출입 불가·차량 상태 문제는 현장 사진을 첨부한다.
- 기상 문제는 사진을 필수로 요구하지 않는다.
- 보충 예약은 원래 예약과 연결해 `배정 대기`로 생성한다.
- 잘못된 처리는 삭제하지 않고 관리자 정정 이력을 추가한다.

### 일정 변경

`방문 예정 → 일정 변경 요청 → 관리자 확인 → 변경된 일정으로 방문 예정`

- 관리자는 요청 승인·대체 일정 제안·거절 중 하나를 선택한다.
- 대체 일정은 고객 수락 후 확정한다.
- 변경 전·후 일정, 요청자, 처리자와 사유를 보존한다.

### 완료 후 고객 품질 문제

`완료 → 고객 문제 제기 → 미완료 → CS·재작업 요청 → 관리자 확인`

- 재작업 승인 시 새 재작업 예약을 생성한다.
- 재작업 완료 후 원래 작업은 `완료(재작업 완료)`로 변경한다.
- 최초 완료와 문제 제기, 미완료 전환 이력은 삭제하지 않는다.

### 일시정지·해지

- 미래 예약은 삭제하지 않고 `취소` 처리한다.
- 취소 사유는 구독 일시정지 또는 구독 해지로 기록한다.
- 일시정지 해제 시 기존 취소 건을 되살리지 않고 앞으로 4주 예약을 새로 생성한다.

### 배정 변경

- 디테일러가 변경을 요청해도 기존 담당자와 `방문 예정` 상태를 유지한다.
- 관리자가 새 담당자를 배정하면 요청을 종료하고 변경 이력을 저장한다.
- 디테일러가 다른 디테일러에게 직접 인계할 수 없다.

## 3. 관리자와 디테일러 권한

### 역할

- 최고관리자: 계정·권한·상품·가격·시스템 설정을 포함한 전체 관리.
- 운영관리자: 고객·차량·단지·예약·배정·작업 결과·CS·재작업 관리.
- 디테일러: 본인에게 배정된 작업과 필요한 고객·차량 정보만 접근.

### 디테일러

- 배정된 차량의 Care Profile과 이전 관리 이력을 확인한다.
- 작업 상태·체크리스트·사진·메모를 입력한다.
- 작업 불가를 직접 확정할 수 있다.
- 현장 관찰 정보와 Care Profile 주의사항은 수정할 수 있다.
- 고객 기본정보, 차량번호·차종·등급, 상품·가격·구독 상태는 수정할 수 없다.
- 기본정보가 다르면 `차량정보 수정 요청`을 보낸다.
- 완료 전에는 본인이 작성한 기록을 수정할 수 있고 완료 후에는 잠긴다.
- 완료 후 정정이 필요하면 관리자가 원본을 보존한 채 정정 기록을 추가한다.
- 고객 연락처와 상세 주차 위치는 작업에 필요한 기간 이후 숨긴다. 정확한 시점은 추후 결정한다.

### 데이터 삭제

- 실제 삭제보다 비활성화를 기본으로 한다.
- 완료 기록과 변경 이력은 임의로 삭제하지 않는다.

## 4. CANOV Care Profile

- `최신 Care Profile`, `방문별 관리 이력`, `Care Profile 변경 이력`을 분리한다.
- 차량 기본정보는 차량번호·모델명·외장 색상·차량 등급만 저장한다.
- 관리 특성은 구조화된 선택 항목과 자유 메모를 함께 사용한다.
- 외장 특이사항, 오염 특성, 작업 주의사항, 고객 관리 선호를 기록한다.
- 세부 선택 항목은 우현의 제공 범위 자료를 받은 뒤 확정한다.
- 주의 부위 사진, 위치 태그, 설명, 발견 방문, 등록자, 최초 등록일, 최근 확인일을 저장한다.
- 주의사항은 유효·변경·해제 상태로 관리하고 삭제하지 않는다.
- 매 방문 작업 전에 `변경 없음` 또는 `변경 사항 등록`을 반드시 선택한다.

작업 시작 전 순서:

`차량 확인 → Care Profile 확인 → 변경 없음/변경 등록 → 작업 전 사진 → 작업 시작`

## 5. 고객 공개 정보와 내부 기록

### 고객 공개

- 차량 기본정보 일부, 방문일, 작업 상태와 작업 항목.
- 고객 공개용 작업 전후 사진과 주의사항.
- 고객 요청 반영 결과, 관리 이력 요약, 다음 방문일.
- CS·재작업 진행 상태.
- 본인 인증 후 전체 고객 공개용 관리 이력을 차량별로 조회한다.

### 내부 전용

- 디테일러 인계 메모, 작업 불가 증빙, 내부 품질 메모.
- 배정 변경 사유, 관리자 정정 기록, 직원 평가·교육 내용.
- CS 내부 판단, 책임 구분과 조사 자료.

### 사진 공개

- 필수 작업 전후 사진은 고객에게 자동 공개한다.
- 작업 불가·내부 품질·CS 증빙 사진은 내부 전용이다.
- 작업 전에 발견한 흠집·손상은 당시 사진과 시간을 내부에 먼저 기록하고 완료 리포트에서 고객에게 안내한다.
- 안내 문구는 손상 원인과 책임을 단정하지 않는 관찰 표현을 사용한다.

## 6. 화면 목록과 정보 구조

### 공개 홈페이지·고객 모바일 웹

- 공개 홈페이지 안에 로그인형 `내 차량 관리` 영역을 포함한다.
- 고객용 별도 앱은 첫 범위에 포함하지 않는다.
- 고객 홈은 다음 방문·현재 상태·최근 관리 결과를 우선 표시한다.
- Care Profile 요약, 전체 관리 이력, 방문별 상세, 문의·재작업을 제공한다.

### 디테일러 Android 앱

하단 메뉴:

- 오늘의 작업
- 전체 일정
- 작업 이력
- 내 정보

알림은 상단 버튼으로 제공한다. 오늘의 작업은 단지별로 묶어 표시하지만 디테일러는 자신에게 배정된 오늘 작업의 순서를 단지와 관계없이 변경할 수 있다. 순서는 내부용이며 고객에게는 시간대만 안내한다.

작업 상세 탭:

- 차량·예약
- Care Profile
- 작업 전 사진
- 체크리스트
- 작업 후 사진
- 품질·완료

탭은 자유롭게 이동할 수 있으나 필수 조건을 충족해야 완료 버튼이 활성화된다.

### 관리자 웹

- 여러 독립 메뉴보다 통합 운영 대시보드를 중심으로 구성한다.
- 중앙 핵심 영역은 오늘의 작업 진행과 디테일러 배정 현황이다.
- 오늘 작업은 표 형식으로 표시하고 상태 카드·필터·검색을 제공한다.
- 예약, 차량, Care Profile, 디테일러, 품질, CS는 오른쪽 상세 패널 또는 필요한 설정 화면으로 연다.

## 7. 입력·버튼·오류 처리

- 차량은 예약 목록에서 선택한 뒤 화면의 정보와 실제 차량이 일치한다는 `차량 확인` 버튼으로 확인한다.
- 번호판 재입력과 자동 인식은 첫 버전에 포함하지 않는다.
- 상품별 필수 사진 항목은 최고관리자가 설정한다.
- 카메라 촬영과 갤러리 선택을 모두 허용한다.
- 사진 유형은 작업 전·작업 후·주의사항·내부 증빙으로 구분한다.
- 오프라인에서도 현장 완료가 가능하며 사진과 기록을 기기에 임시 보관해 자동 동기화한다.
- 동기화 전에는 `완료·동기화 대기`로 표시하고 고객 완료 리포트는 사진 동기화 후 발송한다.
- 체크리스트는 완료·해당 없음·문제 발생으로 입력한다. 해당 없음과 문제 발생은 사유가 필수다.
- 디테일러가 자체 품질 확인 후 완료하고 관리자는 위험 작업과 표본 작업을 사후 검수한다.
- 고객 재작업 요청은 방문 기록·문제 유형·설명이 필수이고 사진은 선택이다.
- 관리자 배정은 표의 버튼과 확인창을 사용하며 개별·일괄 배정을 모두 제공한다.
- 일정 변경 화면은 승인·대체 일정 제안·거절을 제공한다.
- 최초 서비스는 홈페이지 신청서를 사용한다.
- 운영 가능 단지를 검색 선택하고 없는 단지는 서비스 지역 요청으로 접수한다.
- 차량 등급은 고객이 선택하고 관리자가 확정한다.
- 일반 입력은 임시 자동 저장하고 중요한 상태 변화는 확인 버튼으로 확정한다.

## 8. 데이터베이스 논리 구조

- 고객 한 명이 여러 차량을 가질 수 있다.
- 정기관리 계약과 방문 예약은 차량별로 분리한다.
- 차량마다 대표 고객 1명만 관리 이력에 접근한다.
- 한 단지에는 여러 방문 그룹을 만들 수 있고 계약은 방문 그룹 하나에 연결한다.
- 상품·가격·방문 조건은 가입 당시 계약 버전에 보존한다.
- 현재 상태와 상태 변경 이력을 함께 저장한다.
- 방문 예약은 차량별로 만들고 같은 단지·날짜의 예약을 작업 그룹으로 묶는다.

주요 데이터 영역:

- 사용자·역할·권한
- 고객·차량
- 아파트·방문 그룹
- 상품·가격 버전
- 차량별 계약과 자동 예약
- 작업 그룹·배정·상태 이력
- Care Profile·주의사항·사진·변경 이력
- 체크리스트 템플릿·버전·결과
- 품질 검수
- CS·재작업·상담 대화
- 알림·결제·감사 이력

## 9. 알림·메신저·결제

### 메시지와 인증

- 카카오톡 채널을 기본 알림·상담 채널로 사용한다.
- 중요한 알림의 카카오 발송 실패 시 SMS로 대체한다.
- 홈페이지 상담 버튼은 카카오톡 채널로 연결한다.
- 고객 모바일 웹은 휴대전화 인증번호로 본인 인증한다.

### Claude CS 에이전트

- 카카오톡 채널 상담을 먼저 자동화한다.
- 승인된 FAQ·상품·가격·정책에 근거해 답변한다.
- 인증 후 본인 예약·작업 상태와 다음 방문을 조회한다.
- 일정 변경과 품질 문제·재작업 요청을 접수하고 관리자에게 전달한다.
- 일정 변경 확정, 취소, 해지, 환불, 재작업 승인과 분쟁 판단은 관리자가 수행한다.
- 답변 근거가 없거나 민감한 문의는 상담원에게 연결한다.

### 결제

- 차량별 월 카드 자동결제.
- 최초 가입일에 결제하고 이후 매월 같은 날짜에 자동결제한다.
- 다음 달에 같은 날짜가 없으면 해당 월 마지막 날 결제한다.
- 한 결제 주기의 지정 요일에 따라 4회 또는 5회 방문하며 이용료는 동일하다.
- 결제 실패 후 3일 동안 재시도하며 유예기간의 예정 방문은 유지한다.
- 계속 실패하면 계약을 `결제 보류`로 바꾸고 미래 예약을 취소한다.
- 결제 복구 후 계약을 활성화하고 앞으로 4주 예약을 새로 생성한다.
- 구체 결제대행사와 환불 기준은 미정이다.

### 알림 시점

- 방문 전날 일정·예상 시간대 안내.
- 작업 완료 및 사진 동기화 후 완료 리포트 발송.
- 지연·작업 불가·일정 변경 등 중요 사건은 발생 즉시 안내.

## 11. 랜딩 페이지 첫 배포 방식

- A안으로 확정한다: 비공개 미리보기 주소에서 검증한 뒤 사용자 승인 후 공개한다.
- 진행 순서는 `로컬 기본 검사 → 비공개 미리보기 배포 → 사용자 검토·수정 → 공개 승인 → 공개 배포`로 한다.
- 비공개 미리보기에는 테스트 데이터만 사용하며 실제 고객 개인정보를 입력하거나 저장하지 않는다.
- 공개 승인 전 모바일·데스크톱 반응형, 주요 문구, 가격 표시, 신청 흐름, 카카오톡 연결과 오류 상태를 확인한다.
- 공개 배포는 사용자 승인 없이 자동으로 진행하지 않는다.

## 12. 비공개 미리보기의 고객 신청 기능 범위

- A안으로 확정한다: 테스트용 저장소를 연결해 신청 정보 입력, 입력값 검증, 제출, 저장 결과와 관리자 확인 흐름까지 검증한다.
- 비공개 미리보기에서는 실제 고객 개인정보를 사용하지 않고 `테스트 신청`임을 명확히 표시한 가상 데이터만 사용한다.
- 테스트 저장소와 향후 운영 저장소를 분리하며, 테스트 신청 데이터는 운영 저장소로 자동 이전하지 않는다.
- 정상 제출 시 고유 접수 식별값과 접수 시각을 저장하고, 관리자가 제출 내용을 확인할 수 있어야 한다.
- 제출 버튼을 빠르게 여러 번 눌러도 동일 신청이 중복 저장되지 않도록 한다.
- 입력값이 잘못되면 해당 항목 가까이에 이해하기 쉬운 오류를 표시하고, 다른 정상 입력값은 유지한다.
- 저장 실패 시 성공으로 표시하지 않으며 재시도 방법을 안내한다.
- 비공개 미리보기의 관리자 확인 방식은 전체 관리자 웹보다 작은 검증 범위로 구성하고, 최종 기술 조합 확정 시 구체 도구를 결정한다.
- 운영 저장소 연결과 실제 개인정보 수집 시작은 별도의 사용자 승인 후 진행한다.

## 13. 신청 완료 후 고객 안내

- 1차는 A안으로 확정한다: 신청 완료 화면에 접수 결과, 예상 연락 절차와 카카오톡 상담 버튼을 제공한다.
- 완료 화면에는 접수 식별값을 표시하고 고객이 신청이 정상 접수되었는지 확인할 수 있게 한다.
- 비공개 미리보기에서는 실제 카카오톡·SMS 자동 메시지를 발송하지 않는다.
- 후속 운영 단계에서 C안을 추가해 카카오톡 또는 SMS 자동 알림을 연결한다.
- 자동 알림 추가 전 발송 사업자, 고객 동의, 발송 문구, 실패 재시도, 카카오 실패 시 SMS 대체, 발송 이력과 비용 기준을 확정한다.
- 자동 알림이 실패해도 신청 데이터가 사라지거나 중복 접수되지 않도록 신청 저장과 메시지 발송을 분리한다.

## 14. 비공개 미리보기 접근 보호

- A안으로 확정한다: 비밀번호 또는 승인된 계정으로 인증한 사용자만 비공개 미리보기에 접속할 수 있게 한다.
- 주소를 아는 것만으로 접속할 수 있는 공개형 미리보기는 사용하지 않는다.
- 검색엔진 노출 차단을 함께 적용하되, 검색 차단만으로 접근 보호를 대신하지 않는다.
- 비밀번호, 접근 토큰과 서비스 키는 소스 코드나 Git에 저장하지 않는다.
- 브라우저 화면에 포함된 클라이언트 코드만으로 비밀번호를 비교하지 않고 배포·접근 제어 계층에서 인증한다.
- 선택한 배포 도구가 비밀번호 방식을 지원하지 않으면 승인 계정 방식으로 보호한다. 보호 수준을 낮추려면 사용자 승인을 다시 받는다.
- 비공개 미리보기에는 테스트 데이터만 사용하며 실제 고객 개인정보와 운영 저장소를 연결하지 않는다.

## 15. 랜딩 페이지 기술 조합

- 수정된 A안으로 확정한다: Astro + TypeScript, Supabase 테스트 프로젝트, Cloudflare Workers와 Cloudflare Access를 사용한다.
- 최신 Astro Cloudflare 어댑터의 동적 기능은 Cloudflare Pages가 아니라 Workers를 대상으로 하므로 기존 개발도구 계획의 Pages 후보를 Workers로 수정한다.
- 정적 브랜드 콘텐츠와 신청 API를 같은 Astro 프로젝트에서 관리하되, 신청 처리는 서버 엔드포인트에서 수행한다.
- 첫 미리보기에서도 Workers를 중간 계층으로 사용한다. 서버 검증, 접수 식별값, 서버 시각, 중복 방지와 후속 카카오톡·SMS 자동 알림 확장을 같은 경계에서 처리하기 위해서다.
- 단순 INSERT만 필요하고 추가 서버 로직이 전혀 없는 범위에서는 브라우저에서 Supabase로 직접 저장하는 구성을 대안으로 유지한다.
- 직접 저장 대안을 사용할 때는 브라우저용 publishable key만 사용하고 INSERT 외 SELECT·UPDATE·DELETE를 차단하며, RLS뿐 아니라 컬럼 제약·입력 제한·스팸 방지를 함께 적용한다.
- `WITH CHECK (true)`만 둔 익명 INSERT 정책은 임의 데이터와 자동화된 대량 요청을 막지 못하므로 최종 보안 정책으로 사용하지 않는다.
- 서버용 secret key 또는 기존 service role key는 Workers의 암호화된 환경 변수에서만 사용하며 브라우저 코드, 로그와 Git에 노출하지 않는다.
- Cloudflare Access는 스테이징·미리보기 호스트에만 적용하고 실제 고객용 공개 운영 도메인에는 적용하지 않는다.
- 비용 수치는 기술 요구사항으로 고정하지 않고 배포 직전에 공식 요금표와 실제 사용량을 다시 확인한다.

## 16. 테스트 신청 관리자 확인 방식

- B안으로 확정한다: Cloudflare Access로 보호된 읽기 전용 최소 확인 화면을 제공한다.
- 개발 지식이 없는 운영 인수자도 별도 데이터베이스 도구 없이 신청 목록과 상세를 확인할 수 있어야 한다.
- 목록에는 테스트 표시, 접수번호, 접수 시각, 아파트, 차량 구분, 연락 희망 방식을 우선 표시한다.
- 신청 상세에서는 테스트 입력 내용을 확인하되 연락처 등 민감 가능 정보는 목록에서 일부 마스킹한다.
- 접수번호·아파트 검색과 기본 필터를 제공한다.
- 첫 버전에는 수정, 삭제, 일괄 처리, 파일 내보내기와 데이터베이스 설정 기능을 제공하지 않는다.
- 관리자 확인 화면과 조회 API는 공개 운영 도메인에 노출하지 않고 Access로 보호된 미리보기 호스트에서만 사용한다.
- 양도 전 운영 인수자의 승인 이메일을 Access에 등록하고 짧은 사용 안내서를 제공한다.
- 전체 관리자 웹 개발 단계에서 이 화면을 정식 신청 관리 기능으로 확장한다.

## 17. 간단한 차량 점검·보충 범위

- B안으로 확정한다: 첫 출시 서비스 방향에 타이어 공기압·워셔액 같은 간단한 점검과 보충을 포함한다.
- 여기서 `정비`는 차량 수리·분해·고장 진단·법정 점검을 의미하지 않는다.
- 타이어 공기압은 차량 제조사 권장 기준을 확인할 수 있고 검증된 장비와 작업 기준이 준비된 경우에만 점검·보충한다.
- 워셔액은 사용 제품, 혼합 가능 여부, 보충 한도와 누수·이상 발견 시 중단 기준을 작업 절차에 포함한다.
- 점검값, 보충 여부, 작업자, 시각과 이상 발견 내용을 방문 기록에 남긴다.
- 안전하게 수행할 수 없거나 차량별 기준을 확인할 수 없으면 작업하지 않고 사유를 기록해 고객과 관리자에게 안내한다.
- 엔진오일, 냉각수, 브레이크액, 배터리 정비와 기타 수리·부품 교환은 별도 결정 전 범위에 포함하지 않는다.
- 정확한 제공 항목, 소요 시간, 비용, 고객 동의, 체크리스트와 책임 기준은 우현의 자료와 운영 기준을 받아 확정한다.

## 18. 간단한 점검과 보충의 제공 방식

- B안으로 확정한다: 안전하게 수행 가능한 간단한 상태 점검은 기본 서비스에 포함하고, 실제 보충은 고객 동의와 차량별 기준 확인 후 진행한다.
- 고객 동의가 없거나 차량별 권장 기준·사용 제품을 확인할 수 없으면 보충하지 않는다.
- 보충하지 못한 경우 점검 결과, 미실시 사유와 고객이 확인할 사항을 방문 결과에 남긴다.
- 고객이 보충에 동의했더라도 누수, 손상, 경고 표시와 비정상 상태가 발견되면 작업을 중단하고 안내한다.
- 점검 결과와 실제 보충 수행 여부를 구분해 기록하며, 단순히 체크리스트를 선택한 것을 보충 완료로 처리하지 않는다.
- 점검은 기본 서비스로 정했지만 현재 월 이용료에 그대로 포함할지 가격을 조정할지, 보충 재료비·추가요금을 둘지는 우현의 상품 자료와 원가 기준을 받은 후 확정한다.

- A. 가입 시 모든 간단한 보충에 포괄적으로 한 번 동의하고 철회 전까지 적용한다.
