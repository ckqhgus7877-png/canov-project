# CANOV 랜딩 페이지 완료 조건과 핵심 검증 시나리오 v0.1

작성일: 2026-09-16  
상태: 기획 Q&A 결정사항을 반영한 첫 검증 기준. 상품·가격 세부 자료와 개인정보 정책 확정 후 보완한다.

## 1. 목적

첫 랜딩 페이지가 CANOV의 브랜드 방향을 정확히 설명하고, 고객 신청을 테스트 저장소에 안전하게 제출하며, 공개 전 비공개 미리보기에서 주요 흐름을 검증할 수 있는지를 판단한다.

진행 단계는 다음과 같다.

`로컬 기본 검사 → 비공개 미리보기 배포 → 테스트 신청 검증 → 사용자 검토·수정 → 공개 승인 → 공개 배포`

## 2. 첫 범위

- 브랜드 인트로와 슬로건 `Your Car, Always Cared For.`
- 차량 관리가 미뤄지는 문제와 CANOV의 출발 질문
- 첫 신청 이후 매번 예약하지 않아도 이어지는 정기 방문 방식
- 차량별 CANOV Care Profile
- 방문할수록 축적되는 관리 이력
- 담당자가 달라져도 유지되는 표준 작업 기준과 품질 확인
- 타이어 공기압·워셔액 같은 간단한 점검과 보충 방향. 수리·분해·진단 서비스로 확대해 표현하지 않음
- 서비스·가격 안내. 세부 제공 범위와 차종 기준은 자료 수령 대기로 표시
- 운영 가능 단지 검색과 서비스 지역 요청
- 테스트용 고객 신청서와 제출 결과 확인
- 카카오톡 상담 연결

## 3. 첫 범위에서 제외

- 고객 로그인과 `내 차량 관리`
- 실제 고객 개인정보 수집과 운영 저장소 연결
- 실제 카카오톡·SMS 자동 알림 발송
- 결제와 환불
- 전체 관리자 웹
- 디테일러 Android 앱
- 확정되지 않은 세차 제공 범위, 차종 등급과 추가 옵션

## 4. 기능별 완료 조건

### LP-01 비공개 미리보기

- 공개 주소와 분리된 미리보기 환경에서 실행된다.
- 검색엔진에 노출되지 않도록 설정한다.
- 비밀번호 또는 승인된 계정으로 인증한 사용자만 접속할 수 있다.
- 접근 인증은 클라이언트 화면이 아닌 배포·접근 제어 계층에서 처리한다.
- 테스트 환경임을 화면에서 구분할 수 있다.
- 운영 주체 정보가 확정 전임을 표시하고 실제 개인정보를 입력하지 말라고 안내한다.
- 실제 운영자로 오인할 임의의 이름·연락처를 사용하지 않는다.
- 사용자 승인 전 공개 배포가 자동 실행되지 않는다.

### LP-02 브랜드와 핵심 서사

- 문제 → 출발 질문 → 정기 방문 → Care Profile → 누적 이력 → 표준 작업·품질 확인 → 신청·상담 순서가 자연스럽게 연결된다.
- `신청 없이도 관리`는 최초 신청마저 필요 없다는 의미로 표현하지 않는다.
- `정비`는 타이어 공기압·워셔액 같은 승인된 간단한 점검·보충 범위로 설명하고 수리·분해·고장 진단·법정 점검까지 제공하는 것처럼 표현하지 않는다.
- 자료 속 예시 이미지를 실제 CANOV 작업 사례나 동일 차량의 전후 사진으로 오인하게 표시하지 않는다.

### LP-03 서비스와 가격 표시

- 월 이용료와 매주 1회 방문 원칙을 현재 승인된 기획과 일치하게 표시한다.
- 한 결제 주기에 지정 요일이 5회 있어도 추가 요금이 없다는 기준을 오해 없이 안내한다.
- SUV, 대형 SUV·승합·특수 차종과 세부 작업 범위의 미정 사항을 확정 정보처럼 표시하지 않는다.
- 간단한 점검·보충의 세부 항목, 고객 동의와 가격이 확정되기 전에는 자동 제공 또는 무료 제공을 약속하지 않는다.
- 상태 점검은 기본 제공 방향으로 설명하고, 실제 보충은 고객 동의와 차량별 기준 확인이 필요함을 구분한다.
- 보충 동의를 모든 항목에 포괄 적용한다고 표현하지 않고 차량별·항목별 선택과 철회가 가능함을 안내한다.
- 가격과 제공 범위는 나중에 교체 가능한 기준정보로 관리하고 화면 여러 곳에 서로 다른 값이 생기지 않게 한다.

### LP-04 운영 단지 검색과 지역 요청

- 운영 가능한 단지를 검색·선택할 수 있다.
- 검색 결과가 없을 때 서비스 지역 요청으로 이동할 수 있다.
- 비슷한 단지명이 있어도 주소 또는 지역 정보로 구분할 수 있다.
- 로딩, 결과 없음과 조회 실패 상태를 서로 다르게 안내한다.

### LP-05 테스트 신청서

- 신청 흐름 검증에 필요한 이름, 휴대전화, 아파트, 차량 모델·차량 구분과 연락 희망 방식을 입력할 수 있다.
- 비공개 미리보기에서는 실제 이름과 전화번호 대신 명확한 테스트 값을 사용하도록 안내한다.
- 차량 등급은 고객의 선택값과 관리자의 추후 확정값을 구분할 수 있는 구조로 저장한다.
- 차량번호, 상세 주차 위치, Care Profile과 보충 항목별 동의는 첫 신청서에서 수집하지 않는다.
- 첫 공개 버전에는 마케팅 수신 동의 항목을 표시하거나 그 동의값을 수집하지 않는다.
- 마케팅 동의는 실제 캠페인 계획과 사용자 승인이 생긴 뒤 상담 신청 처리 안내와 분리된 선택 항목으로만 추가한다.
- 상담 종료·철회 시 지체 없이 파기하고 미응답·미계약 신청은 고객의 마지막 의미 있는 응답 또는 무응답 시 접수일로부터 최대 90일 후 자동 파기한다.
- 신청 버튼 전에 처리 항목, 목적, 보유기간과 온라인 신청 선택 권리를 표시한다.
- 핵심 내용은 바로 표시하고 전문은 입력값을 잃지 않는 펼쳐보기로 제공하며 개인정보 처리방침 링크를 함께 제공한다.
- 필수 개인정보 동의 체크박스나 동의값을 만들지 않고 적용 안내 문구 버전과 시각을 기록한다.
- 실제 공개 전 고객 요청 처리 고지안의 법적 근거와 최종 문구를 실제 운영 흐름에 맞춰 검토한다.
- 비공개 미리보기에서는 실제 문의 주소를 임의로 만들지 않고 개인정보 문의 경로가 확정 전임을 표시한다.

### LP-06 입력 검증

- 필수값 누락과 형식 오류는 해당 입력 항목 가까이에 구체적으로 표시한다.
- 오류가 없는 입력값은 검증 실패 후에도 유지된다.
- 오류 메시지는 색상만으로 구분하지 않고 텍스트로 설명한다.
- 잘못된 입력 상태에서는 제출 성공 화면을 표시하지 않는다.

### LP-07 테스트 저장과 중복 방지

- 유효한 신청은 테스트 저장소에 한 번 저장된다.
- 저장 결과에 고유 접수 식별값과 서버 기준 접수 시각이 포함된다.
- 제출 버튼을 빠르게 반복해서 눌러도 같은 신청이 중복 저장되지 않는다.
- 저장 중에는 진행 상태를 표시하고 중복 입력을 막는다.
- 저장 실패를 성공으로 표시하지 않으며 입력 내용을 유지한 채 재시도 방법을 제공한다.
- 테스트 데이터는 운영 저장소로 자동 이전되지 않는다.
- 신청 브라우저는 Supabase 서버용 비밀 키를 받지 않으며, 첫 구현에서는 Cloudflare Workers의 신청 API를 통해 저장한다.

### LP-08 신청 완료 안내

- 정상 저장이 확인된 뒤에만 완료 화면을 표시한다.
- 완료 화면에 접수 결과, 접수 식별값, 예상 연락 절차와 카카오톡 상담 버튼을 제공한다.
- 첫 미리보기에서는 실제 카카오톡·SMS 자동 메시지를 발송하지 않는다.
- 자동 알림은 후속 운영 단계에서 별도 연동한다.

### LP-09 관리자 확인

- 권한이 있는 확인 주체가 테스트 신청 목록과 개별 내용을 확인할 수 있다.
- 화면의 접수 식별값과 저장소의 기록이 일치한다.
- 관리자가 확인할 수 없더라도 고객에게 거짓 완료 상태를 표시하지 않는다.
- Cloudflare Access로 보호된 읽기 전용 최소 확인 화면을 제공한다.
- 목록에는 테스트 표시, 접수번호, 접수 시각, 아파트, 차량 구분과 연락 희망 방식을 표시한다.
- 접수번호·아파트 검색과 기본 필터를 제공하고 목록의 연락처는 일부 마스킹한다.
- 수정, 삭제, 일괄 처리와 파일 내보내기는 제공하지 않는다.
- 개발 지식이 없는 운영 인수자가 별도 데이터베이스 도구 없이 사용할 수 있어야 한다.

### LP-10 카카오톡 상담 연결

- 상담 버튼이 승인된 CANOV 카카오톡 채널로 연결된다.
- 링크를 열 수 없는 환경에서는 대체 안내를 제공한다.
- 신청 완료 여부와 상담 버튼 클릭 여부를 혼동하지 않게 구분한다.

### LP-11 반응형·접근성·기본 품질

- 대표 모바일·태블릿·데스크톱 화면 폭에서 가로 잘림이나 겹침 없이 사용할 수 있다.
- 키보드만으로 주요 링크와 신청서를 이동·제출할 수 있다.
- 입력 항목에는 연결된 이름표가 있고 포커스 위치를 확인할 수 있다.
- 핵심 이미지에는 대체 텍스트를 제공하고 본문과 버튼의 대비를 확인한다.
- 치명적·높음 등급 오류가 0건이어야 공개 승인을 요청할 수 있다.

## 5. 핵심 검증 시나리오

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| LT-01 | 모바일과 데스크톱에서 처음부터 신청 영역까지 탐색 | 핵심 서사가 같은 순서로 보이고 콘텐츠가 잘리거나 겹치지 않는다. |
| LT-02 | 운영 가능한 단지 검색 | 정확한 단지를 선택하고 신청서로 이어진다. |
| LT-03 | 운영하지 않는 단지 검색 | 결과 없음 안내와 서비스 지역 요청 경로가 보인다. |
| LT-04 | 단지 조회 서버 실패 | 결과 없음과 구분되는 실패 안내 및 재시도 수단이 보인다. |
| LT-05 | 필수값을 비우고 제출 | 각 누락 항목에 오류가 표시되고 저장되지 않는다. |
| LT-06 | 잘못된 형식의 테스트 연락처 입력 | 형식 오류를 안내하고 다른 입력값은 유지한다. |
| LT-07 | 유효한 테스트 신청 제출 | 테스트 저장소에 1건 저장되고 완료 화면의 접수 식별값이 일치한다. |
| LT-08 | 제출 버튼을 빠르게 여러 번 선택 | 신청은 한 번만 저장된다. |
| LT-09 | 저장 중 네트워크 또는 서버 오류 | 성공으로 표시하지 않고 입력값을 유지하며 재시도를 안내한다. |
| LT-10 | 오류 복구 후 다시 제출 | 중복 없이 1건이 저장되고 정상 완료 화면이 보인다. |
| LT-11 | 완료 화면의 카카오톡 상담 버튼 선택 | 승인된 채널로 연결되거나 사용할 수 없는 환경의 대체 안내가 보인다. |
| LT-12 | 관리자 확인 경로에서 접수 조회 | 고객 화면과 같은 접수 식별값·시각·입력 내용이 확인된다. |
| LT-13 | 테스트 저장소와 운영 설정 확인 | 운영 데이터 연결이 없고 테스트 데이터가 운영 저장소로 이동하지 않는다. |
| LT-14 | 키보드만으로 신청 완료 | 초점이 논리적으로 이동하고 모든 필수 기능을 사용할 수 있다. |
| LT-15 | 가격·제공 범위 문구 검토 | 간단한 점검·보충과 수리·진단의 경계가 명확하고, 확정값과 자료 수령 대기 항목이 구분된다. |
| LT-16 | 개인정보 처리 안내 표시 | 핵심 내용이 신청 버튼 전에 보이고 전문을 펼쳐도 입력값이 유지되며 모바일·키보드로 확인할 수 있다. |
| LT-17 | 운영 주체 정보 공개 게이트 | 확정 전 표식이나 필수 운영 정보 누락이 있으면 실제 개인정보를 받는 공개 신청 기능이 열리지 않는다. |
| LT-18 | 개인정보 처리 근거 공개 게이트 | 고지안의 최종 적합성이 확인되지 않았거나 필수 동의 방식이 함께 남으면 공개 신청 기능이 열리지 않는다. |
| LT-19 | 개인정보 문의 경로 확인 | 전용 이메일과 카카오톡·CS 보조 경로가 실제 담당자에게 도착하며 개인 휴대전화 번호가 공개되지 않는다. |
| LT-20 | 역할 주소 운영권 확인 | CANOV 보유 도메인의 역할 주소로 수신·회신할 수 있고 운영 인수자가 다중 인증·복구·갱신 권한을 관리한다. |
| LT-21 | 별도 업무용 메일함 확인 | 개인정보 문의가 일반 상담과 분리되어 보존되고 자동화 장애 시에도 담당자가 수동으로 확인·회신할 수 있다. |
| LT-22 | 개인정보 문의 자동화 권한 | AI는 분류·고정 접수 안내·초안까지만 수행하고 실제 개인정보 조치는 사람 승인 없이 실행되지 않는다. |
| LT-23 | 첫 공개 개인정보 권리 요청 경로 | 전용 이메일·카카오톡·CS와 본인 확인 절차가 안내되고, 미승인 셀프서비스 신청·상태 조회 화면은 노출되지 않는다. |
| LT-24 | 개인정보 권리 요청 내부 관리 | 일반 상담과 분리된 최소 기록만 Access 보호 화면에서 관리되고, 미승인 접근·직접 DB 접근은 차단되며 모든 변경에 감사기록이 남는다. |

개인정보 수명주기의 자동 검증은 `docs/planning/CANOV-privacy-data-policy-v0.1.md`의 시나리오를 함께 적용한다.

## 6. 공개 승인 조건

- LT-01부터 LT-24까지 실제 검사 결과가 기록되어 있다.
- 치명적·높음 오류는 0건이다.
- 보통·낮음 오류는 영향, 우회 방법과 수정 일정이 기록되어 있다.
- 실제 고객 개인정보가 테스트 저장소, 로그, 화면 캡처와 Git에 포함되지 않았다.
- 테스트 신청 데이터의 정리 여부를 확인했다.
- 운영자·사업자 명칭, 개인정보 문의 연락처, 처리방침 시행일과 신청 처리 책임 주체가 확정되어 처리 안내 전문·처리방침·신청 화면에 일치한다.
- 상담 신청 개인정보 처리 고지안의 법적 근거와 최종 문구가 실제 운영 흐름을 기준으로 검토되어 있다.
- CANOV 전용 개인정보 이메일과 카카오톡·CS 보조 문의 경로의 수신 테스트가 완료되어 있다.
- 역할 주소의 회신, 메일 인증, 다중 인증, 복구와 도메인·메일 자동 갱신 설정이 확인되어 있다.
- 별도 업무용 메일함과 자동화 최소 권한·장애 시 수동 처리 경로가 확인되어 있다.
- AI 제공업체 검토, 입력 마스킹, 초안 사람 승인, 위험 문의 이관과 외부 입력 격리 기준이 확인되어 있다.
- 확정 전 표식과 미리보기용 표시값이 공개 화면과 설정에 남아 있지 않다.
- 모바일과 데스크톱의 최종 화면을 사용자가 검토했다.
- 사용자에게 수정사항과 남은 미정 항목을 보고하고 명시적인 공개 승인을 받았다.

## 7. 후속 C안: 자동 알림 추가 조건

카카오톡 또는 SMS 자동 알림은 공개 운영 준비 단계에서 다음 조건을 확정한 뒤 추가한다.

- 발송 사업자와 계정
- 고객 수신 동의와 개인정보 처리 기준
- 승인된 메시지 문구와 발송 시점
- 재시도 횟수와 중복 발송 방지
- 카카오 발송 실패 시 SMS 대체 기준
- 발송 성공·실패 이력과 비용 확인
- 신청 저장 성공과 메시지 발송 실패를 분리해 처리하는 방식
