랜딩 페이지는 Astro + TypeScript, Supabase 테스트 프로젝트, Cloudflare Workers + Access 조합으로 확정합니다. 관리자 웹의 배포 기술은 구현 전 별도로 확정합니다.

## 고객 CS 자동화 단계 제안

| 단계 | 자동화 범위 | 조건 |
|---|---|---|
| A. 상담 지원 | 문의 분류, 답변 초안, 상담 요약 | 운영자가 검토하고 직접 발송 |
| B. 공개 문의 자동응답 | 승인된 FAQ·서비스 안내 자동 답변 | 근거 없음과 미정 정책은 배정 디테일러 또는 사장 연결 |
| C. 인증 정보 안내 | 본인 예약·작업 상태 조회 및 답변 | 고객 인증, 데이터 접근 권한, 감사 기록 |
| D. 업무 처리 | 예약 변경·취소 등 허용된 작업 | 업무별 정책과 최종 확인 절차 확정 후 검토 |

첫 출시는 A·B와 제한된 읽기 전용 C단계를 적용한다. 본인 인증 후에도 예약 시간대·단지 공통 상태·본인 차량 완료·예외만 안내하며 D단계의 변경·취소·환불 등 실제 업무 실행은 제외한다. 배정 고객의 현장·작업 상담은 회사 소유 채널 안에서 담당 디테일러에게 연결하고, 환불·보상·차량 손상·결제 분쟁·개인정보 변경과 정책 예외는 사장에게 연결한다. AI 답변과 사람 답변을 구분하고 사람 답변에는 회사 소속과 사장이 승인한 업무용 표시명을 표시한다. 직원 개인 전화번호·카카오톡은 고객에게 공개하지 않으며 별도 사무직원은 전제하지 않는다.

한 현장에서 하루 약 40~60대를 처리하는 운영을 전제로 차량별 위치·순번·진행 상황을 직원이 수동 상담하지 않는다. AI는 시스템에 기록된 예약 시간대, 단지 공통 상태와 차량별 완료·예외만 안내하고 차량 미확인·출입·안전 등 고객 조치가 필요한 예외만 담당 디테일러에게 이관한다.

고객 표시 상태는 단지 `방문 예정·현장 작업 중·현장 종료`와 본인 차량 `예약됨·완료·예외/확인 필요`로 제한한다. 순번·정확한 위치·세부 단계·예상 완료 시각은 표시하지 않으며 AI가 추측하지 않는다.

현장 책임자는 단지 시작·종료를 각각 한 번만 처리하고, 차량 완료·예외는 디테일러의 기존 체크리스트 완료·예외 등록과 동시에 생성한다. GPS로 상태를 자동 확정하지 않으며 오프라인 전송은 중복 없이 복구하고 잘못된 상태는 원본을 보존한 관리자 정정으로 처리한다.

사장은 방문 그룹마다 현장 책임자 한 명과 필요 시 현장 대체 책임자 한 명을 지정한다. 동시에 한 명만 활성화하며 단독 방문은 자동 지정한다. 책임자 권한은 해당 방문 그룹의 공통 상태와 집계에 한정하고 다른 직원 배정 고객의 상세정보 접근 권한을 추가하지 않는다.

고객·차량에는 기본 담당 디테일러를 지속적으로 유지하고 특정 방문의 담당자를 별도 저장한다. 사장만 임시·영구 재배정할 수 있으며 임시 접근은 방문 후 제거하고 영구 변경은 미해결 상담·Care Profile·주의사항·예정 예약을 인계한다. 과거 작업의 실제 수행자는 변경하지 않는다.

임시 변경은 적용 방문과 새 업무용 표시명, 영구 재배정은 새 기본 담당과 적용일만 영향을 받는 고객에게 회사 채널로 안내한다. 직원 개인 사유·내부 인사정보·개인 연락처는 포함하지 않고 발송 성공·실패를 기록한다.

담당 변경 안내는 사장이 배정을 최종 확정한 뒤 승인 템플릿으로 자동 발송한다. 중복 방지, 제한 재시도, 실패 알림과 정정 메시지를 지원하며 알림 실패가 배정·접근 권한 적용을 되돌리지 않게 한다.

고객의 담당 변경 요청은 AI가 구조화해 하나의 검토 건으로 만들고 사장 화면에 전달한다. 자동 재배정은 금지하며 사장이 일정·작업량·숙련도·미해결 상담·분쟁·안전을 확인한 뒤 유지·임시 변경·영구 변경을 확정한다. 확정 전에는 기존 권한과 배정을 바꾸지 않고 긴급 안전 사유는 기존 담당자에게 자동 노출하지 않은 채 사장에게 즉시 이관한다.

변경 요청 원문·상세 사유는 사장만 보고 디테일러에게는 필요한 조치와 결정만 전달한다. 일반 건은 1영업일 내 결정 또는 예정 안내, 안전·중대 분쟁은 즉시 알림과 운영시간 내 30분 확인을 목표로 하며 당사자 간 직접 대면을 강제하지 않는다.

디테일러의 고객 연락처·상세 주차 위치 접근은 배정 방문 전날부터 작업 완료·동기화까지로 제한한다. 예외 연장은 사장이 사유와 만료 시각을 지정해야 하며 배정 취소·변경·종료 시 즉시 회수하고 과거 이력에서는 마스킹한다.

## Codex 주 개발과 Claude 추가 검토 절차

2026-09-29 사용자가 확정했습니다. 기존의 ‘Claude 구현 담당·Codex 2차 검증’ 절차를 대체합니다. 서비스 기획의 58개 Q&A와 별도의 협업 결정입니다.

1. Codex가 기획을 정리하고 기능별 작은 작업과 확인 가능한 완료 조건을 작성합니다.
2. Codex가 구현, 관련 테스트와 오류 수정을 진행하고 기획 일치, 권한, 데이터 연결, 실패 처리와 회귀 영향을 확인합니다.
3. 인증·권한, 개인정보, DB 구조·마이그레이션, 결제, AI의 업무 실행 범위 등 중요한 변경은 Codex가 Claude 추가 검토 필요성과 이유를 사용자에게 제안합니다. 단순 수정에 불필요한 검토 단계를 추가하지 않습니다.
4. 검토가 필요하면 Codex가 전달용 프롬프트를 작성합니다. 변경 목적·범위, 관련 요구사항과 Q&A 번호, 기준 버전과 관련 코드·변경 내역, 실제 검사 결과, 알려진 문제와 확인할 위험을 포함합니다. 비밀키와 실제 고객 개인정보는 포함하지 않습니다.
5. 사용자가 프롬프트와 필요한 자료를 Claude에 전달하고 검토 결과를 Codex에게 가져옵니다. 이 절차는 사용자의 수동 전달 방식입니다.
6. Codex가 각 지적의 타당성을 확인해 반영하거나 근거를 기록하고, 필요한 수정과 재검증을 수행합니다. 검토가 필요한 변경에는 검토 대기·수신·반영·재검증 상태를 남기며 검토 전에는 해당 검토를 완료로 보고하지 않습니다.
7. 출시 전 고객 신청부터 작업 완료 확인까지 전체 흐름을 통합 검증합니다. Claude 검토와 실제 기능 검증 결과를 구분합니다.

## 개발 도구와 운영용 AI 선택

- Codex·Claude의 개발 협업 방식과 출시된 서비스의 AI 제공업체는 별도로 결정합니다.
- 첫 CS 기능의 시험 제공업체는 OpenAI API로 확정합니다. 이는 최종 운영 제공업체 확정이 아닙니다. 실제 카노브 상담의 근거 정확성, 인증·권한 준수, 사람에게 이관해야 하는 문의의 분류, 응답 속도와 문의당 비용을 검증한 뒤 운영 채택 여부를 결정합니다.
- 시험 결과에는 사용한 모델·프롬프트·지식 버전·평가 데이터 버전, 성공·실패 건수, 응답 시간과 추정 비용을 함께 기록해 이후 제공업체 또는 모델 비교가 가능하게 합니다. 실제 고객 대화를 평가에 사용하려면 개인정보 기준과 승인을 먼저 충족합니다.
- AI 호출 부분을 예약·권한·DB 처리와 분리합니다. 제공업체 변경 시 프롬프트와 도구 호출을 다시 검증합니다.
